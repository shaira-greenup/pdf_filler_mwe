# PDF Form Filler

Fills a known AcroForm PDF from a typed, validated data object. Runtime is **Bun**. Language is **TypeScript**. No build step.

This repo is both a working reference implementation — one real government form, fully wired through all four steps below — and the recipe for adding more forms. The hard rules and hazards below are properties of AcroForm PDFs and `pdf-lib` in general. They are not specific to the one form currently implemented here, and they apply unchanged to every form added after it.

## Scope

Each form is a fixed, known target, wired up ahead of time: one blank PDF fixture, one Zod schema, one mapping module, one filled PDF written to disk. There is no server, no UI, no upload, and no dynamic template registry that resolves a form at request time. Do not build a runtime dispatcher — adding a form means running the workflow below and committing its output, not registering it somewhere at runtime. The fill logic must also run unmodified in a browser (a SolidJS app is the eventual consumer), so keep it free of Bun/Node-specific APIs — isolate file I/O at the edges (see Bun API notes).

## Stack

- Runtime: Bun (native TypeScript, ESM, top-level await)
- PDF: `pdf-lib`
- Validation: `zod`
- Tests: `bun test` (built in)
- Occasionally, per-form, one-time: `qpdf` — a workstation tool, not a project dependency. See Known hazards.

Install with `bun add`. Run with `bun run scripts/name.ts`. Never use npm, tsx, ts-node, nodemon, or a bundler. Do not add a build step, do not scaffold with `bun create`, do not add vitest or jest.

## Files (this form's instance of the pattern)

```
fixtures/blank-form.pdf     the real form, committed, never modified
fixtures/fields.txt         field dump, generated by scripts/inspect.ts
fixtures/sample-data.json   realistic but fake input
scripts/schema.ts           Zod schema for the typed input shape
scripts/mapping.ts          schema keys -> exact PDF field names/values
scripts/template.ts         template hash guard
scripts/inspect.ts          dump fields
scripts/fill.ts             fill and write output
scripts/fill.test.ts        hostile-input and structural regression tests
out/                        generated PDFs, gitignored
```

This flat layout is one form's worth of files. It has not yet been decided how multiple forms will coexist in this repo — per-form subdirectories, separate projects, or something else. When a second form is added, make that call explicitly and update this section to describe the convention actually chosen, rather than letting a layout emerge by accident.

## Hard rules

These are the failure modes that do not announce themselves. Follow them exactly, for every form.

1. **Never invent a field name.** Read that form's `fields.txt` (generated fresh by `scripts/inspect.ts`) and use those exact strings. If a required field is absent from the PDF, throw with the missing name. Never fall back to a guess, a fuzzy match, or a silent skip.
2. **Always call `form.updateFieldAppearances()` before `pdf.save()`.** Without it the values render blank in Chrome and mobile viewers while looking correct in Acrobat.
3. **Load with `{ ignoreEncryption: true }`.** This only suppresses pdf-lib's `EncryptedPDFError` — it does not decrypt anything. It is enough for forms with permissions-only protection (an empty owner password, no real cipher on content). It is not enough for forms with a real cipher on their streams — see Known hazards.
4. **Do not flatten.** Not by default. It is a separate, explicit variable, and pdf-lib's flatten is weak on checkboxes and radio groups.
5. **Do not set calculated fields.** If a field has a JavaScript calculation action (its `/AA` dict has a `/C` entry), set its inputs instead. Acrobat recomputes derived fields on open and will discard what you wrote.
6. **Radio groups and checkboxes use export values from the PDF**, not `"Yes"`/`"true"`. `scripts/inspect.ts` must print the valid options for every checkbox and radio group, and the fill code must use those literal strings.
7. **A checkbox field can have multiple widgets, each with its own on-value — effectively an unflagged radio group.** pdf-lib's public `PDFCheckBox.check()` and `acroField.setValue()` only ever recognize the *first* widget's on-value; calling them on a multi-widget checkbox silently limits you to that one option, no matter what you intended. `scripts/inspect.ts` must enumerate every widget's on-value, not just the first. See `mapping.ts`'s `selectCheckboxOption` for the pattern that selects any widget's value directly and rejects one that matches none of them.
8. **A widget can be present, correctly valued, and still invisible.** The `/F` annotation flag's Hidden bit (value 2) is a static, spec-level rendering directive set directly in the PDF — not something only the form's own JavaScript can toggle, and not something pdf-lib will ever clear on its own, since pdf-lib never executes the form's JavaScript. A form that gates whole sections behind a lead question ("Is anyone employed?") ships those sections Hidden by default. `scripts/inspect.ts` must report each widget's Hidden state. When filling a field inside a gated section, decide explicitly whether to clear the Hidden flag (see `mapping.ts`'s `unhide`) — never assume that setting a value makes it visible.
9. **Read back every field after writing** — reload the *saved* bytes, not just the in-memory document — and compare to the intended value. Throw on mismatch. This is the cheapest guard against truncation, calculated-field overwrites, wrong export values, and gated sections left invisible by mistake.
10. **Assert the template hash on load.** Store the SHA-256 of the blank fixture and fail at startup if it changes, so an upstream re-publish surfaces immediately instead of silently producing blank or subtly wrong forms.

## Bun API notes

Use Bun's file APIs at the I/O edges rather than `node:fs`:

```ts
const bytes = new Uint8Array(await Bun.file("fixtures/blank-form.pdf").arrayBuffer());
await Bun.write("out/filled.pdf", await pdf.save());
```

For the template hash:

```ts
const hasher = new Bun.CryptoHasher("sha256");
hasher.update(bytes);
const digest = hasher.digest("hex");
```

## Workflow: adding a form

Follow this sequence for every form, in order. Stop and get each step's output reviewed before continuing — do not run ahead speculatively. None of these steps are specific to the form currently implemented here; only the field names, schema shape, and hash constant change per form.

1. **Obtain the blank PDF.** If `PDFDocument.load` throws or produces a flood of "invalid object" parse warnings even with `ignoreEncryption: true`, the form likely carries a real cipher on its content, not just permissions-only protection — see Known hazards before assuming pdf-lib itself is broken.
2. **Inspect** — a script prints every field for this form: name, type, current value, Hidden state per widget, and — for every checkbox and radio group — the full set of valid export values across *all* widgets (hard rule 7). Write the output to that form's `fields.txt`.
3. **Fill** — a fill script sets three or four hardcoded fields for this form and writes a filled PDF. Stop here. The output must be opened and checked by a human in both Acrobat and Chrome.
4. **Map** — a Zod schema for this form's input shape, plus a mapping module from schema keys to this form's exact PDF field names and export values. Replace the hardcoded values with parsed sample data.
5. **Verify** — a hostile-input test suite using `bun test`: a name outside WinAnsi/Latin-1, a maximum-length value on an unbounded field, every real checkbox/radio value exercised individually, any gated section's Hidden-flag round-trip, and any multi-widget checkbox's rejection of an invalid value. Confirm no throw on valid-but-extreme input, and a clear throw — naming the field and, where applicable, the valid options — on genuinely invalid input.

## Known hazards

- **Some published forms are encrypted with a real cipher** (e.g. AES-128 / `AESV2`, PDF Standard Security Handler), not just a permissions-only owner password. `ignoreEncryption: true` does not decrypt this — pdf-lib has no decryption support at all (confirmed: neither `pdf-lib` nor the `@cantoo/pdf-lib` fork implement it). Symptom: dozens of "invalid object" parse warnings, then a crash on something structural like page-tree traversal, because compressed object streams decompress to ciphertext garbage instead of throwing a clear encryption error. Fix: decrypt once, outside the project, with `qpdf --decrypt source.pdf fixtures/blank-form.pdf` (or equivalent) and commit the decrypted fixture. `qpdf` is a workstation tool, not a project dependency — it's only needed again if that form's source is later re-published.
- **Non-ASCII characters throw in `form.updateFieldAppearances()` (font encoding), not at save time.** WinAnsi cannot encode them. Plain Western accented characters and curly apostrophes are actually within WinAnsi/CP1252's range and do *not* throw (confirmed: `"José"`, `"O'Brien"`). The real triggers are anything outside Latin-1: Vietnamese/Polish/Turkish diacritics, Cyrillic, CJK, emoji (confirmed: `"Nguyễn"`, `"Łukasz"`, `"İstanbul"`). Do not paper over this with a `.replace()` that strips characters — surface it, and if it needs solving, embed a font via `@pdf-lib/fontkit`.
- **Duplicate field names across pages share one value.** Setting one sets all. This is by design in the PDF spec, not a bug to work around.
- **Text overflow is silent.** `setText` never complains when a value clips or auto-shrinks past legibility. Only a rendered image reveals it.
- **pdf-lib is effectively unmaintained.** If something is broken at the library level, `@cantoo/pdf-lib` is a maintained drop-in fork. Do not switch to it preemptively — confirm the same failure reproduces there first. It shares pdf-lib's parsing core, so most failures, including the encryption one above, reproduce identically.

## Verification

You cannot see the rendered PDF. "The script ran without error" and "the form is correctly filled" are different claims — never report the second based on the first, for any form. After any change that affects output, state plainly that the PDF needs to be opened and checked by a human, and say which fields to look at.
