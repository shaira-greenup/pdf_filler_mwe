# PDF Form Filler

Fills a known AcroForm PDF from a typed, validated data object. Runtime is **Bun**. Language is **TypeScript**. No build step.

This repo is both a working reference implementation — one real government form, fully wired through all four steps below — and the recipe for adding more forms, driven by a small CLI (`scripts/cli.ts`). The hard rules and hazards below are properties of AcroForm PDFs and `pdf-lib` in general. They are not specific to the one form currently implemented here, and they apply unchanged to every form added after it.

## Scope

Each form is a fixed, known target, wired up ahead of time: one blank PDF fixture, one Zod schema, one mapping module, one filled PDF written to disk — every form is committed to the repo, not resolved dynamically. There is no server, no UI, no upload, and no live production service that picks a template per end-user request at runtime. Do not build that. This is a different thing from `scripts/cli.ts`: a developer-invoked command-line tool, run at a terminal, that takes a form id as an argument to add or exercise a form during development. The CLI is dev tooling for building out the pattern below; it is not, and must not become, a runtime dispatcher serving live requests. The fill logic itself must also run unmodified in a browser (a SolidJS app is the eventual consumer), so keep it free of Bun/Node-specific APIs — isolate file I/O at the edges (see Bun API notes).

## Stack

- Runtime: Bun (native TypeScript, ESM, top-level await)
- PDF: `pdf-lib`
- Validation: `zod`
- Tests: `bun test` (built in)
- CLI argument parsing: `node:util`'s `parseArgs` (built in — no CLI-parsing dependency)
- Occasionally, per-form, one-time: `qpdf` — a workstation tool, not a project dependency. See Known hazards.

Install with `bun add`. Never use npm, tsx, ts-node, nodemon, or a bundler. Do not add a build step, do not scaffold with `bun create`, do not add vitest or jest, do not add a CLI-parsing library (commander/yargs/meow) — `node:util`'s `parseArgs` is sufficient for this CLI's five subcommands.

```
    smokeTest.ts              mechanical fill-everything check, no business schema needed

    exportSchema.ts            JSON Schema export logic (CLI's `schema`)

  smokeTest.test.ts          runs the generic smoke test against every form under forms/

  blank-form.pdf              the real form, committed, never modified

                              line ("SHA-256: ...") is the hash hard rule 10 checks
  schema.ts                   Zod schema for this form's typed input shape (starts
                              empty for a freshly-init'd form - see Workflow)
  mapping.ts                   schema keys -> exact PDF field names/values for this
                              form (starts as a no-op for a freshly-init'd form)
  sample-data.json             realistic but fake input for this form
  sample-data.schema.json      JSON Schema, generated by `cli.ts schema`
  fill.test.ts                 this form's business-specific hostile-input and

```

When a form has no hand-authored business fields yet (freshly `init`'d), its `schema.ts`/`mapping.ts` are effectively empty and every field falls through to the generic layer in `genericFields.ts` — this is a valid, immediately-usable state, not a placeholder that must be filled in before the form is useful. `cli.ts smoke-test <id>` proves this: it fills every fillable field mechanically with zero business schema.

## Hard rules

These are the failure modes that do not announce themselves. Follow them exactly, for every form.

1. **Never invent a field name.** Read that form's `fields.txt` (generated fresh by `cli.ts inspect <id>`) and use those exact strings. If a required field is absent from the PDF, throw with the missing name. Never fall back to a guess, a fuzzy match, or a silent skip.
2. **Always call `form.updateFieldAppearances()` before `pdf.save()`.** Without it the values render blank in Chrome and mobile viewers while looking correct in Acrobat.
3. **Load with `{ ignoreEncryption: true }`.** This only suppresses pdf-lib's `EncryptedPDFError` — it does not decrypt anything. It is enough for forms with permissions-only protection (an empty owner password, no real cipher on content). It is not enough for forms with a real cipher on their streams — `scripts/lib/encryption.ts` detects this case up front; see Known hazards.
4. **Do not flatten.** Not by default. It is a separate, explicit variable, and pdf-lib's flatten is weak on checkboxes and radio groups.
5. **Do not set calculated fields.** If a field has a JavaScript calculation action (its `/AA` dict has a `/C` entry), set its inputs instead. Acrobat recomputes derived fields on open and will discard what you wrote. `genericFields.ts`'s `isFillable()` excludes these automatically.
6. **Radio groups and checkboxes use export values from the PDF**, not `"Yes"`/`"true"`. `cli.ts inspect` prints the valid options for every checkbox and radio group, and the fill code must use those literal strings.
7. **A checkbox field can have multiple widgets, each with its own on-value — effectively an unflagged radio group.** pdf-lib's public `PDFCheckBox.check()` and `acroField.setValue()` only ever recognize the *first* widget's on-value; calling them on a multi-widget checkbox silently limits you to that one option, no matter what you intended. `cli.ts inspect` enumerates every widget's on-value, not just the first. See `genericFields.ts`'s `selectCheckboxOption` for the pattern that selects any widget's value directly and rejects one that matches none of them.
8. **A widget can be present, correctly valued, and still invisible.** The `/F` annotation flag's Hidden bit (value 2) is a static, spec-level rendering directive set directly in the PDF — not something only the form's own JavaScript can toggle, and not something pdf-lib will ever clear on its own, since pdf-lib never executes the form's JavaScript. A form that gates whole sections behind a lead question ("Is anyone employed?") ships those sections Hidden by default. `cli.ts inspect` reports each widget's Hidden state (`isHidden` in `genericFields.ts`). When filling a field inside a gated section, decide explicitly whether to clear the Hidden flag (`unhide` in `genericFields.ts`) — never assume that setting a value makes it visible.
9. **Read back every field after writing** — reload the *saved* bytes, not just the in-memory document — and compare to the intended value. Throw on mismatch. This is the cheapest guard against truncation, calculated-field overwrites, wrong export values, and gated sections left invisible by mistake.
10. **Assert the template hash on load.** The expected SHA-256 lives in that form's own `fields.txt` (its first line, written by `cli.ts inspect`) — not a separate hardcoded constant — so it can't drift out of sync with itself. `scripts/lib/hash.ts`'s `assertTemplateHash` fails at startup if the PDF has changed since `fields.txt` was generated, so an upstream re-publish surfaces immediately instead of silently producing blank or subtly wrong forms.

## Bun API notes

Use Bun's file APIs at the I/O edges rather than `node:fs`:

```ts
const bytes = new Uint8Array(await Bun.file("forms/<id>/blank-form.pdf").arrayBuffer());
await Bun.write("out/<id>/filled.pdf", await pdf.save());
```

For the template hash:

```ts
const hasher = new Bun.CryptoHasher("sha256");
hasher.update(bytes);
const digest = hasher.digest("hex");
```

## Workflow: adding a form

Run these as `bun run scripts/cli.ts <subcommand> <id> ...`. Stop and get each step's output reviewed before continuing — do not run ahead speculatively. None of this is specific to the form currently implemented here; only the field names, schema shape, and per-form hash change per form.

1. **`init <id> <pdf-path>`.** Copies the PDF into `forms/<id>/blank-form.pdf` (never references an external path — hard rule 1 assumes a fixed, locally-owned fixture), runs the encryption pre-flight (fails fast with an actionable message if the source carries a real cipher — see Known hazards), writes `fields.txt`, scaffolds an empty `schema.ts`/no-op `mapping.ts`, and seeds `sample-data.json` with one synthesized valid placeholder per fillable field. The form is immediately usable through the generic layer after this — no business mapping required yet.
2. **`smoke-test <id>`** (or a raw path, for a form that hasn't been `init`'d at all). Mechanically fills every fillable field, saves, reloads, and verifies every value round-trips and every Hidden section it touched is now visible. Confirms the pattern holds for this PDF's actual structure — multi-widget checkboxes, gated sections, MaxLength-bounded fields — without asserting what any field means.
3. **Hand-author the business layer**, once you know what some of the fields actually mean: fill in `schema.ts` with named, typed keys for those fields, and `mapping.ts` with the exact PDF field names/export values they map to. Everything else stays on the generic layer, addressed by raw field name.
4. **`fill <id> [--data path] [--out path]`.** Validates `sample-data.json` (business keys through the hand-authored schema, everything else through the PDF's own derived structure), applies it, writes the PDF, and reads the saved bytes back to confirm every field landed as intended. Stop here. The output must be opened and checked by a human in both Acrobat and Chrome.
5. **`schema <id>`** whenever the business schema changes, to refresh `sample-data.schema.json` — a standard JSON Schema document combining the hand-authored and derived shapes, useful for handing to anything that needs to generate valid input data for this form without re-deriving its structure itself.
6. **Add `fill.test.ts`** for this form's business-specific behavior: a name outside WinAnsi/Latin-1, a maximum-length value on an unbounded field, every real checkbox/radio value exercised individually, any gated section's Hidden-flag round-trip, and any multi-widget checkbox's rejection of an invalid value. The mechanical smoke test from step 2 already covers the generic layer automatically via `scripts/smokeTest.test.ts` — this step is only for behavior specific to the fields you named in step 3.

## Known hazards

- **Some published forms are encrypted with a real cipher** (e.g. AES-128 / `AESV2`, PDF Standard Security Handler), not just a permissions-only owner password. `ignoreEncryption: true` does not decrypt this — pdf-lib has no decryption support at all (confirmed: neither `pdf-lib` nor the `@cantoo/pdf-lib` fork implement it). Left undetected, the symptom is dozens of "invalid object" parse warnings, then a crash on something structural like page-tree traversal, because compressed object streams decompress to ciphertext garbage instead of throwing a clear encryption error. `scripts/lib/encryption.ts` now detects the known-fatal ciphers (`AESV2`/`AESV3`, `/V >= 5`) up front, from the raw trailer, and every path that loads a PDF (`cli.ts init`, `loadForm.ts`) fails with an actionable message instead of that cryptic crash. Fix: decrypt once, outside the project, with `qpdf --decrypt source.pdf forms/<id>/blank-form.pdf` (or equivalent) and commit the decrypted fixture. `qpdf` is a workstation tool, not a project dependency — it's only needed again if that form's source is later re-published. A bare legacy `/Encrypt` entry with no such cipher info (older RC4/permissions-only forms) is treated as ambiguous, not blocking, since those have loaded successfully before.
- **Non-ASCII characters throw in `form.updateFieldAppearances()` (font encoding), not at save time.** WinAnsi cannot encode them. Plain Western accented characters and curly apostrophes are actually within WinAnsi/CP1252's range and do *not* throw (confirmed: `"José"`, `"O'Brien"`). The real triggers are anything outside Latin-1: Vietnamese/Polish/Turkish diacritics, Cyrillic, CJK, emoji (confirmed: `"Nguyễn"`, `"Łukasz"`, `"İstanbul"`). Do not paper over this with a `.replace()` that strips characters — surface it, and if it needs solving, embed a font via `@pdf-lib/fontkit`.
- **Duplicate field names across pages share one value.** Setting one sets all. This is by design in the PDF spec, not a bug to work around.
- **Text overflow is silent.** `setText` never complains when a value clips or auto-shrinks past legibility. Only a rendered image reveals it.
- **pdf-lib is effectively unmaintained.** If something is broken at the library level, `@cantoo/pdf-lib` is a maintained drop-in fork. Do not switch to it preemptively — confirm the same failure reproduces there first. It shares pdf-lib's parsing core, so most failures, including the encryption one above, reproduce identically.

## Verification

You cannot see the rendered PDF. "The script ran without error" and "the form is correctly filled" are different claims — never report the second based on the first, for any form. After any change that affects output, state plainly that the PDF needs to be opened and checked by a human, and say which fields to look at.
